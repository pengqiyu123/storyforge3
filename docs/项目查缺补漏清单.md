# 项目查缺补漏清单

## 漏洞 1：只有写入，没有删除

### 具体表现

当前系统大量能力围绕“创建、生成、写入、导出”展开，但缺少对应的删除能力。

典型缺口：

- 章节可以生成，但缺少章节删除；
- plan 可以生成，但缺少 plan 删除；
- truth 可以写入，但缺少 truth 删除或作废；
- export 可以生成，但缺少导出文件删除；
- run 记录可以产生，但缺少清理策略；
- provider 可以导入，已有移除能力，但作品侧数据删除链路不完整。

### 影响

- 写错章节后无法清理；
- dogfood 产生的幽灵章节无法安全移除；
- ch3/ch4 这类“有 truth/export 但无正文”的异常只能诊断，不能处理；
- 长期使用后数据目录会累积无效产物；
- 用户会觉得系统只能不断生成，不能管理作品；
- agent 一旦误写，缺少回滚和删除入口。

### 严重程度

**P1。**

短期不阻塞生成，但会严重影响真实使用和数据治理。

### 建议

新增统一删除能力，至少覆盖：

```text
删除章节正文
删除章节 plan
删除章节 truth
删除章节 export
删除章节 run 记录
删除整章全部产物
```

删除必须是高风险 Action：

- 二次确认；
- 显示将删除哪些文件；
- 默认进入回收站或生成删除快照；
- 不允许静默物理删除；
- 删除后触发 reconcile 刷新。

## 漏洞 2：章节列表有诊断，但缺少处理入口

### 具体表现

当前 reconciliation 能识别：

- 有 Truth 但无状态；
- 有导出但无正文；
- 有状态但无正文；
- 产物不一致。

但 UI 主要是展示异常原因，没有明确的处理按钮。

### 影响

- 用户知道数据坏了，但不知道怎么修；
- PM/Codex 只能手动进文件夹处理；
- 异常章节会持续污染下一章判断；
- “只写一章却看到后续章节”的问题可能反复出现。

### 严重程度

**P1。**

### 建议

增加“异常处理”入口：

```text
查看异常详情
生成修复预览
删除孤儿产物
补 state
忽略本次异常
恢复快照
```

第一阶段只做 preview，不自动执行。

---

## 漏洞 3：下一章判断仍可能被幽灵产物污染

### 具体表现

如果系统只用 `max_chapter + 1` 推导下一章，那么孤儿产物会污染章节进度。

例如：

```text
第 1、2 章正常
第 4 章有残留 truth
系统可能误判下一章是第 5 章
```

### 影响

- 跳过中间章节；
- 用户不理解真实进度；
- agent 可能继续在错误章节号上生产；
- 章节列表和创作流程错位。

### 严重程度

**P1。**

### 建议

reconcile 应提供：

```text
valid_chapter_count
highest_contiguous_chapter
next_writable_chapter_no
has_blocking_inconsistency
```

下一章应基于“从第 1 章开始连续有效章节”推导，而不是最高章节号。

---

## 漏洞 4：Run 失败后缺少用户可理解的恢复路径

### 具体表现

当前已有 run/reconcile 方向，但失败后用户仍可能只看到：

```text
needs_review
数据不一致
运行失败
```

却不知道下一步该做什么。

### 影响

- dogfood 卡住；
- 用户只能求助开发者；
- agent-mode 下失败不可自助处理；
- AutoDirector 继续推进时风险更高。

### 严重程度

**P1。**

### 建议

每个失败 run 应给出：

```text
失败阶段
失败原因
已产生产物
是否可恢复
推荐动作
可执行入口
```

推荐动作示例：

```text
重试当前阶段
从下一阶段继续
回滚到快照
删除本章产物
标记人工处理
```

## 漏洞 5：阶段产物有展示框架，但详情不完整

### 具体表现

章节页已有 Run Viewer 和阶段标签，但部分阶段仍偏占位：

- audit 详情不完整；
- revise diff 不完整；
- approval record 不完整；
- export record 不完整；
- run stage artifact 不完整。

### 影响

- 用户看到阶段完成，但不知道完成了什么；
- 审计和修订过程不可复盘；
- 失败后难判断是否需要人工介入。

### 严重程度

**P2。**

### 建议

每个阶段都应有标准产物视图：

```text
plan：规划内容
Draft：正文与字数
Audit：问题列表与阻断级别
Revise：修改摘要与 diff
Approve：批准记录与 hash
Truth：提取事实
Export：导出文件与格式
```

## 漏洞 6：生成能力强，人工编辑后的再处理链路弱

### 具体表现

用户可以手动编辑正文，但编辑后系统如何处理后续状态不够清晰。

例如：

- 编辑后 audit 是否失效？
- truth 是否需要重新提取？
- export 是否需要重新生成？
- approval hash 是否过期？

### 影响

- 用户改了正文，但系统仍显示旧审计/旧导出；
- Truth 与正文不一致；
- 导出文件可能不是最新版本。

### 严重程度

**P1/P2。**

### 建议

正文保存后应标记下游产物过期：

```text
text_updated
requires_reaudit
truth_stale
export_stale
approval_invalidated
```

前端明确提示：

```text
正文已修改，建议重新审计/重新提取 Truth/重新导出。
```

---

## 漏洞 7：缺少“版本”和“回收站”概念

### 具体表现

当前有快照，但日常删除、覆盖、重新生成缺少轻量版本机制。

### 影响

- 用户害怕删除；
- agent 误生成后难恢复；
- 删除功能如果直接物理删除风险很高；
- 快照粒度可能过重。

### 严重程度

**P2。**

### 建议

增加轻量回收站：

```text
.trash/chapters
.trash/plans
.trash/truth
.trash/exports
```

删除动作默认移动到 trash，并记录：

```text
deleted_at
deleted_by
reason
original_path
related_chapter
```

## 漏洞 8：Provider 导入后缺少完整可用性闭环

### 具体表现

Provider 可以导入，但用户仍可能遇到：

- 无 key provider 被展示；
- 导入成功但 verify 失败；
- verify 成功但生成失败；
- active provider 路径与 runtime 不一致；
- 错误原因不够清楚。

### 影响

- 用户以为模型配置好了，实际章节生成失败；
- dogfood 被环境问题阻断；
- 调试成本高。

### 严重程度

**P1。**

### 建议

Provider 面板应显示：

```text
已导入
已启用
已验证
最后验证时间
最后失败原因
实际使用 endpoint
```

---

## 漏洞 9：错误提示不够持久和可诊断

### 具体表现

部分错误提示会自动消失，且缺少复制诊断信息。

### 影响

- 用户没看清错误；
- 无法把错误发给开发者；
- dogfood 记录不完整。

### 严重程度

**P2。**

### 建议

错误卡片应持久显示，并提供：

```text
复制诊断信息
查看原始错误
查看 run_id
查看阶段
查看 provider
查看耗时
```

---

## 漏洞 10：缺少统一 Action 风险等级

### 具体表现

系统中不同动作风险不同，但 UI 和 API 没有统一表达：

- 生成：中风险；
- 覆盖：高风险；
- 删除：高风险；
- 导出：中风险；
- 恢复快照：高风险；
- 切换 provider：中风险。

### 影响

- 高风险动作可能缺少确认；
- agent 调用时缺少权限边界；
- 前端无法统一展示风险提示。

### 严重程度

**P2。**

### 建议

引入 Action 元信息：

```text
action_name
risk_level
requires_confirmation
side_effects
affected_files
rollback_strategy
```

删除、恢复、覆盖类动作必须先接入。

## 优先级建议

### P0 / 立即关注

暂无必须停工的 P0，但 Provider runtime 路径不一致若仍存在，应视为 P0。

### P1 / 下一阶段必须补

1. 章节删除与产物删除能力；
2. 异常章节处理入口；
3. next_writable_chapter_no；
4. Run 失败恢复建议；
5. 正文编辑后的下游产物失效标记；
6. Provider 可用性闭环。

### P2 / 产品可用性增强

1. 阶段产物详情展示；
2. 回收站；
3. 错误诊断复制；
4. Action 风险等级；
5. 版本管理。

---

## 总结

当前 StoryForge3 最大的逻辑漏洞不是“不能生成”，而是：

```text
能不断写入，但缺少删除、修复、恢复、失效、诊断这些反向治理能力。
```

项目要从生成工具变成真正可长期使用的创作工作台，必须补齐：

```text
写入 + 删除 + 修复 + 回滚 + 诊断 + 版本
```

其中最优先的是：

> **章节删除 / 产物删除 / 异常章节处理 / 下一章正确推导。**

## 唯一 ELEVATE：#1 最小 discard 原语

**为什么这一条破例**：ch3/4 幽灵已证明"写出错 → 需清理"是**已发生**痛点（PM 手工 5 层 discard），不是猜想。dogfood 产 ch3 若失败/质量差，需要"清 ch3 重产"；手工不可持续。

**最小版**（不做 UI / 回收站 / 版本系统，agent-mode 走 API/CLI）：
- `DELETE /api/books/{id}/chapters/{n}`（或 `storyforge3 discard-chapter {book} {n}`）：删该章全部产物——text/plan/truth JSON + **truth.db 该章行** + exports + snapshots + pipeline.jsonl 该章行。
- **强制备份**到 `books/{id}/_trash/ch{n}/`（PM 手写脚本的行为固化），不静默物理删。
- 二次确认 + 返回将删文件清单；删除后触发 reconcile 刷新。
- 本质：把 PM 手写的 discard 脚本提升为可复用、有测试的原语。
- **时机**：可与 dogfood 并行（产 ch3 前/中提供，作 redo 保险），**不阻塞** dogfood 启动。

## 排序（方向纠偏后，凌驾本文"优先级建议"）

1. **P1-3 门禁**（引擎最后一项，已下发，后端 only）→ 验收
2. **dogfood 产 ch3**（火山 provider，agent 调 `/run` 全管线）→ 人工读评 ⬅ **当前首要**
3. **#1 最小 discard 原语**（dogfood redo 保险，可与 2 并行）
4. 其余 #2/#4/#5/#6/#7/#9/#10：**全部 DEFER**，等 dogfood 真实痛点驱动，按暴露顺序补

## 一句话

> 清单对"反向治理缺失"的诊断**准**，但**治理工程不能抢在产出之前**。先证明能稳定产 ch3，再按 dogfood 暴露的真实顺序补删除/修复/诊断。**需求驱动，不堆砌。**

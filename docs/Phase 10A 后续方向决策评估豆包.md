# Phase 10A 后续方向决策评估(豆包)

> 日期：2026-06-12\
> 目的：评估 Phase 10A 完成后是否应直接进入 Phase 10B 自动导演 MVP，或先进行《别打了》真实 dogfood，或转向其他优先级任务。\
> 基线依据：用户提供的最新状态为 Phase 10A 已全部完成，后端测试 501 项通过，前端测试 71 项通过，构建 clean。

***

## 1. 执行摘要

建议结论：**不要立即全面进入 Phase 10B。应先执行一轮短闭环 dogfood，再基于 dogfood 结果设计 Phase 10B 指令。**

推荐路径：

```text
Phase 10A 完成
  -> 10A 验收 dogfood：用《别打了》真实生成 1 章
  -> 整理阻塞问题与体验缺口
  -> 修复 P0/P1 阻塞
  -> 输出 Phase 10B 自动导演 MVP 指令
  -> 再进入 Phase 10B 实现
```

核心理由：

1. Phase 10B 是“大工作流编排”阶段，会把建书、世界观、角色、卷纲、章节、审计、truth、导出串成更高层自动化流程。
2. 如果当前章节管线、流式进度 UI、truth 召回、错误恢复尚未经过真实创作验证，直接叠加自动导演会放大问题。
3. 《别打了，我帮你们翻译还不行吗?》已经具备复杂世界观、结构化 world/characters/truth，是最适合验证 StoryForge3 当前能力边界的压力测试书。
4. 一轮 dogfood 不应被视为“拖慢开发”，而是 Phase 10B 的需求发现和风险收敛环节。

最终建议：**选择方向 2，但将其定义为 Phase 10B 前置门禁，而不是另开旁支。**

***

## 2. 当前项目状态判断

### 2.1 已具备的优势

根据最新基线，项目已经完成：

- 后端长任务流式能力；
- SSE `llm:progress` 与前端进度 UI；
- truth 导出前保障；
- 文档治理与 ADR 启用；
- 《别打了》复杂世界观受控数据入库；
- TruthRetriever 能在第 2 章上下文取到第 1 章 truth；
- 后端 501 tests、前端 71 tests、build clean。

这说明项目已经从“功能堆叠期”进入“真实可用性验证期”。

### 2.2 仍存在的关键不确定性

虽然测试基线良好，但以下问题无法仅靠单元测试证明：

1. **流式进度 UI 是否真的降低等待焦虑**\
   测试能证明组件渲染，但不能证明用户在真实 LLM 长任务中是否看得懂、是否觉得可控。
2. **复杂世界观下 truth 是否足够支撑续写**\
   已验证第 2 章上下文能取到第 1 章 truth，但还需验证召回内容是否真的帮助草稿质量。
3. **章节质量是否满足真实创作**\
   Prompt、audit、revision 在工程上可用，不代表产出具备连载价值。
4. **错误恢复路径是否清晰**\
   Provider 延迟、限流、半途中断、SSE 断开等问题只有真实运行时才容易暴露。
5. **Phase 10B 的自动导演需求是否准确**\
   如果没有 dogfood 数据，自动导演可能只是把现有步骤机械串联，而不是解决真实作者痛点。

***

## 3. 三个方向评估

## 3.1 方向一：直接进入 Phase 10B 自动导演 MVP

### 内容

立即启动自动导演 MVP 的指令设计与任务拆解，围绕以下能力展开：

- 灵感输入生成 BookConfig；
- 自动生成 world / characters / volume；
- 自动生成前 1-3 章；
- checkpoint / resume；
- 失败重试与人工介入点；
- 前端一键开书向导；
- MCP tool `auto_create_book`。

### 短期收益

1. **战略推进速度快**\
   能迅速进入项目最有产品差异化的阶段。
2. **更接近竞品的自动导演形态**\
   自动导演是 StoryForge3 从“管线控制台”升级为“AI 创作工作台”的关键。
3. **容易形成里程碑叙事**\
   “一句灵感到第一章”比“修 UI 和 dogfood”更容易展示项目价值。

### 长期收益

1. 建立高层 workflow 编排能力；
2. 为未来自动生成多章、整本规划、任务恢复奠定基础；
3. 使 MCP 和前端都能调用统一自动化入口。

### 主要风险

1. **在未验证底层体验前叠加复杂度**\
   自动导演会调用多个现有模块。如果其中任一模块存在真实体验问题，Phase 10B 会把问题放大。
2. **自动导演黑盒化**\
   用户可能看到“一键运行失败”，但不知道失败在建书、世界观、角色、卷纲、起草、审计还是 truth。
3. **需求误判**\
   如果没有真实 dogfood，Phase 10B 可能优先实现错误功能。例如先做“一键生成前三章”，但真实用户最需要的是“失败后从某阶段继续”。
4. **测试复杂度上升**\
   自动导演涉及跨服务、长任务、LLM mock、状态恢复、UI 进度、MCP tool，测试矩阵会明显膨胀。

### 资源需求

- 产品设计：高；
- 后端编排：高；
- 前端向导：中高；
- 测试与 mock：高；
- dogfood 验证：仍不可避免。

### 适用条件

只有在以下条件满足时，才适合直接进入：

- 已有至少一次真实章节 dogfood；
- 流式进度 UI 已确认可理解；
- 章节管线没有明显阻断；
- truth 召回对续写有实际帮助；
- provider 错误路径可接受。

当前虽然工程基线强，但产品体验证据仍不足，因此不建议直接进入全面实现。

***

## 3.2 方向二：先进行一轮内部 dogfood

### 内容

使用《别打了，我帮你们翻译还不行吗?》真实创作一个章节，重点验证：

- Phase 10A 流式进度 UI；
- 第 1 章 truth 对第 2 章上下文的实际帮助；
- plan / draft / audit / revise / truth / export 全流程体验；
- 复杂世界观下的设定保持；
- 长任务等待、错误提示和恢复体验；
- 章节产出是否具备继续创作价值。

### 短期收益

1. **快速发现真实阻塞**\
   单元测试覆盖不到的 UX、LLM、上下文、provider 问题可以集中暴露。
2. **验证 Phase 10A 是否真正有产品价值**\
   流式进度 UI 的价值必须在真实长任务里验证。
3. **为 Phase 10B 设计提供真实需求**\
   自动导演需要知道哪些阶段必须可暂停、哪些输出必须人工确认、哪些错误最常见。
4. **避免盲目扩张**\
   如果章节管线还不稳，自动导演只会放大不稳定性。

### 长期收益

1. 建立 dogfood 作为版本门禁的习惯；
2. 积累真实章节质量评估样本；
3. 形成自动导演的验收语料；
4. 更准确地定义 Phase 10B MVP 范围。

### 主要风险

1. **看起来不像“新功能进展”**\
   dogfood 产出更多是问题列表和改进建议，不如新功能直观。
2. **可能暴露较多问题，导致 Phase 10B 延后**\
   但这是好事，说明问题本来存在，只是提前被发现。
3. **真实 LLM 调用有成本和不确定性**\
   Provider 波动可能影响测试体验，需要记录而不是掩盖。

### 资源需求

- 产品观察：中；
- LLM 调用成本：中；
- 修复问题：取决于发现数量；
- 文档记录：低中。

### 建议执行范围

不要把 dogfood 做成大而全的测试周。建议限定为一个短闭环：

```text
目标：真实生成《别打了》第 2 章
范围：plan -> draft -> audit -> revise（如需要）-> truth -> export
输出：dogfood 记录 + P0/P1 问题清单 + Phase 10B 需求修正
```

### 通过标准

- 能完成一章，不需要绕过系统；
- 流式进度 UI 在 draft 阶段可见且有帮助；
- 第 1 章 truth 被召回，并对第 2 章有实际上下文贡献；
- 审计结果可理解，误判不阻断流程；
- 章节文本达到“可人工编辑后继续连载”的水平；
- 生成过程中的失败或不适点被记录。

## 3.3 方向三：处理其他优先级任务

### 可能内容

其他任务可能包括：

- Rust / Tauri CI 验证；
- 本地 API 安全边界；
- Action Module 抽象；
- RAG / Truth 检索优化；
- 编辑器体验；
- 文档状态修正；
- Provider 错误脱敏；
- 快照 / 删除等高风险动作模块化。

### 短期收益

1. 可以降低已知技术债；
2. 能补齐安全、CI、架构治理等基础问题；
3. 避免直接进入大阶段前堆积隐患。

### 长期收益

1. 提高系统稳定性；
2. 降低 Phase 10B 实现成本；
3. 为 Agent 自动化调用建立更强边界。

### 主要风险

1. **战略主线被稀释**\
   如果没有明确筛选标准，“其他优先级任务”会变成无限清债。
2. **容易陷入工程洁癖**\
   当前项目已经具备较强测试与文档基线，继续先清债可能延迟产品突破。
3. **不一定解决 Phase 10B 的核心不确定性**\
   例如重构 Action Module 很重要，但它不能替代真实章节 dogfood。

### 适用条件

只有当 dogfood 前存在明确阻断时，才应优先处理其他任务。例如：

- 前端无法启动；
- Provider 无法调用；
- 章节保存不可信；
- SSE 进度 UI 明显损坏；
- Git/CI 状态不可信。

否则不建议把“其他任务”放在 Phase 10B 前面作为大方向。

## 4. 不同观点辩论

### 观点 A：应直接进入 Phase 10B

支持理由：

- Phase 10A 已全部完成，测试和构建 clean；
- 自动导演是项目战略主线；
- 继续 dogfood 会拖慢功能推进；
- 很多问题可以在 Phase 10B 开发过程中一起发现和修复。

反驳：

- 测试 clean 证明工程没有明显回归，不证明真实创作体验达标；
- 自动导演不是单点功能，而是多模块叠加器，会放大底层问题；
- 如果没有 dogfood，Phase 10B 的任务拆解容易偏工程想象，而不是用户痛点；
- 一轮小 dogfood 不会显著拖慢进度，反而能避免后续返工。

### 观点 B：应先 dogfood

支持理由：

- Phase 10A 的目标本来就是验证期；
- 《别打了》已经是复杂世界观压力测试书；
- 10A 新增流式进度 UI 必须在真实长任务中验证；
- Phase 10B 的自动导演需要真实流程数据作为输入。

反驳：

- dogfood 可能暴露大量问题，导致阶段推进变慢；
- 真实 LLM 结果有随机性，难以形成稳定结论；
- 可能把团队带入“修小问题”的循环。

回应：

- dogfood 应限定范围，只记录 P0/P1，不无限修所有问题；
- LLM 随机性本身就是产品风险，必须被观察；
- 输出应服务 Phase 10B，不应变成长期维护分支。

### 观点 C：应先处理其他技术债

支持理由：

- 自动导演前需要更强架构边界；
- Action Module、高风险动作、API 安全、CI 都很重要；
- 先补底座可以减少后续重构。

反驳：

- 当前最大不确定性不是“架构是否优雅”，而是“真实作者能否顺畅写下一章”；
- 技术债很多，若无真实 dogfood 排序，很难判断哪些最该先修；
- Phase 10B 前的最佳输入不是抽象重构，而是真实使用证据。

***

## 5. 推荐决策

### 5.1 推荐选择

推荐选择：**方向 2：先进行一轮内部 dogfood。**

但需要明确：

> dogfood 不是替代 Phase 10B，而是 Phase 10B 的前置发现阶段。

### 5.2 推荐顺序

```text
Step 1：同步状态文档
  - current.md / next.md 若仍显示 10A-3 待执行，应更新为 Phase 10A 完成
  - 记录后端 501、前端 71、build clean

Step 2：执行《别打了》第 2 章 dogfood
  - 使用 Web UI，不绕过流程
  - 跑 plan / draft / audit / revise / truth / export
  - 记录耗时、进度 UI、truth 召回、章节质量、错误体验

Step 3：形成 dogfood 结果
  - P0：阻断问题，必须先修
  - P1：影响 Phase 10B 的问题，进入 10B 指令
  - P2：体验优化，进入 10C 或 backlog

Step 4：设计 Phase 10B 指令
  - 根据 dogfood 结果决定 AutoDirectorService 的 MVP 边界
  - 明确哪些阶段自动执行，哪些阶段必须人工确认
  - 明确 checkpoint / resume 的最小实现
  - 明确前端一键开书向导是否一次做完，还是先做后端服务 + MCP

Step 5：进入 Phase 10B 实现
```

## 6. Phase 10B MVP 范围建议

基于当前项目状态，Phase 10B 不应一开始追求“自动生成前三章完整体验”。建议 MVP 收敛为：

### 6.1 MVP 目标

> 用户输入一句灵感，系统生成可审查的书籍基础材料，并能自动推进到第 1 章草稿；每个阶段可见、可暂停、可失败恢复。

### 6.2 建议首版交付

1. `AutoDirectorService`
   - 输入：灵感、题材、平台、目标字数、是否使用复杂世界观模板；
   - 输出：BookConfig、WorldConfig、CharacterList、VolumePlan、第 1 章 plan/draft。
2. Checkpoint / Resume
   - 至少支持从以下阶段恢复：
     - book\_created；
     - world\_created；
     - characters\_created；
     - volume\_planned；
     - chapter\_planned；
     - chapter\_drafted。
3. 人工介入点
   - world 生成后允许确认；
   - characters 生成后允许确认；
   - 第 1 章 draft 前允许确认。
4. SSE 可观察性
   - 每阶段必须有 `pipeline:start/progress/complete/error`；
   - LLM 长输出继续使用 `llm:progress`。
5. 最小前端入口
   - 先做“一键开书向导”的最小版；
   - 不做复杂多页导演台；
   - 重点是阶段可见和失败可恢复。
6. MCP tool
   - `auto_create_book` 可以作为 Phase 10B 后半段；
   - 不应早于服务层稳定。

### 6.3 暂不建议纳入 MVP

- 自动生成前 3 章；
- 完整 RAG；
- 复杂势力/组织模型全量重构；
- 多书并发导演；
- 逐 token 前端渲染；
- 完整导演台 UI。

这些应进入 Phase 10C 或 Phase 10B 后续子阶段。

## 8. 风险控制

### 8.1 Dogfood 阶段风险

| 风险            | 影响                   | 处理                           |
| ------------- | -------------------- | ---------------------------- |
| Provider 慢或限流 | 影响结论                 | 记录为真实风险，不掩盖                  |
| 草稿质量差         | 暴露 prompt/context 问题 | 标为 P1，进入 10B 指令              |
| 进度 UI 不清楚     | 影响长任务体验              | 先修 UI，再进入 10B                |
| truth 召回无效    | 影响自动导演连续性            | 进入 10B/10C 设计约束              |
| 问题过多          | 阶段失焦                 | 只修 P0，P1 纳入 10B，P2 入 backlog |

### 8.2 Phase 10B 阶段风险

| 风险      | 影响      | 缓解                               |
| ------- | ------- | -------------------------------- |
| 自动导演黑盒化 | 用户不信任系统 | 阶段可见、日志可见、失败可恢复                  |
| 生成内容不可控 | 难以人工接管  | 每个产物都可审查、可编辑                     |
| 多模块耦合过高 | 维护困难    | AutoDirector 只编排 Service，不内嵌业务逻辑 |
| LLM 成本高 | 使用门槛高   | 支持阶段确认、取消、重试                     |
| 复杂世界观跑偏 | 章节质量下降  | 强制 truth/context/audit 门禁        |

***

## 9. 最终建议

### 推荐决策

**选择方向 2：先进行一轮内部 dogfood。**

### 决策理由

1. Phase 10A 的核心价值是“真实可观察化”，必须通过真实创作验证；
2. Phase 10B 是更高层自动化，依赖底层章节管线稳定；
3. 《别打了》已经具备复杂世界观压力测试条件，正适合作为 dogfood 样本；
4. Dogfood 结果能直接提升 Phase 10B 指令质量，避免盲目拆解；
5. 其他技术债应由 dogfood 暴露的问题排序，而不是先验无限清债。

### 推荐行动

1. 先同步状态文档，把 Phase 10A 标为完成；
2. 用《别打了》真实生成第 2 章；
3. 产出 dogfood run 记录；
4. 修复阻断级问题；
5. 基于结果设计 Phase 10B 指令；
6. Phase 10B MVP 严格收敛到“一句灵感到第 1 章草稿 + checkpoint/resume + 阶段可见”。

一句话结论：

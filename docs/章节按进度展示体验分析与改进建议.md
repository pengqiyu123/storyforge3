# 章节按进度展示体验分析与改进建议

## 1. 背景与问题描述

从使用者视角看，当前章节展示曾出现一个明显违背创作直觉的问题：

> 明明只写了一章，前端却一次性展示五个章节卡片。

这会让用户产生困惑：

- 我到底写了几章？
- 为什么系统显示第 2、3、4、5 章？
- 这些章节是已经存在、待写，还是系统自动预留？
- 如果现在显示 5 章，那写完第 5 章后第 6 章如何出现？
- 空章节能不能点？点开后会不会误触运行？

这种展示方式会让章节列表从“创作进度视图”变成“章节占位视图”，不利于用户理解真实进度，也不适合当前 StoryForge3 已转向的 agent-mode-first 模型。

---

## 2. 当前实现现状

当前代码已经从旧的固定 5 章启发式，部分迁移到了 reconciliation 真相源。

当前章节列表实现位于：

```text
web/src/components/chapters/ChapterList.tsx
```

现有逻辑：

```ts
const reconciliation = reconcile.data;
const chapters = (reconciliation?.chapters ?? []).filter(hasAnyArtifact);
const maxChapter = reconciliation?.max_chapter ?? 0;
const nextChapter = maxChapter + 1;
```

并通过：

```ts
function hasAnyArtifact(chapter: ChapterConsistency): boolean {
  return chapter.has_text || chapter.has_plan || chapter.has_truth || chapter.has_export || chapter.has_state || chapter.has_run;
}
```

过滤真实存在产物的章节。

也就是说，当前版本已经不再直接使用旧逻辑：

```ts
Math.min(Math.max(book.current_chapter + 2, 5), book.target_chapters || 5)
```

但从产品设计角度看，这个问题仍然值得系统梳理，因为它暴露了章节展示、创作流程、agent 生产、用户引导之间的核心关系。

---

## 3. 从使用者体验角度看，固定展示五章的问题

### 3.1 破坏“写一章，解锁下一章”的自然心智

小说创作是天然线性推进的：

```text
第 1 章完成
  → 第 2 章出现
  → 第 2 章完成
  → 第 3 章出现
```

如果系统一开始展示 5 个章节，用户会误以为：

- 系统已经为我生成了 5 章；
- 这些章节都是待办任务；
- 我需要依次处理这 5 个章节；
- 空章节也可以被点击或运行。

这与实际创作流程不一致。

### 3.2 容易混淆“章节计划”和“章节产物”

章节可以处于不同层次：

| 层次 | 示例 | 是否是真实章节产物 |
|---|---|---|
| 目标章节数 | 本书计划 100 章 | 否 |
| 卷纲章节范围 | 第一卷 1-30 章 | 否 |
| 下一章提示 | 第 2 章待生产 | 否 |
| 规划产物 | `plans/0002.json` | 是 |
| 正文产物 | `chapters/0002.md` | 是 |
| Truth 产物 | `truth/chapter-0002.json` | 是 |
| 导出产物 | `exports/...0002...` | 是 |

固定展示 5 章会把“目标章节”或“占位章节”伪装成“真实章节”，导致用户误判。

### 3.3 会制造进度焦虑

用户只完成了第 1 章，却看到第 2-5 章全部空着，会形成一种“系统提示我还有四章没做”的心理负担。

这对于创作型产品非常不友好。创作工具应强化“已完成”和“下一步”，而不是提前制造大量空任务。

### 3.4 容易诱导误操作

如果空章节卡片可以展开，用户可能会尝试：

- 点击空章节；
- 寻找运行按钮；
- 误以为可以手动生成；
- 在 agent-mode-only 模式下困惑为什么不能操作。

这会和当前产品方向冲突：

```text
章节生产由 agent/API 触发，前端章节页主要负责查看和编辑。
```

### 3.5 章节出现机制不自洽

如果一开始展示 5 章，用户自然会问：

> 写完第 5 章后第 6 章怎么出现？

这说明固定 5 章模式没有清晰的“章节解锁规则”。

合理机制应是：

```text
真实产物章节 + 一个下一章提示器
```

而不是：

```text
固定展示 N 个空章节
```

---

## 4. 对小说创作流程的影响

### 4.1 对创作节奏的影响

小说创作强调连续推进。每一章通常依赖：

- 上一章正文；
- 上一章 Truth；
- 当前卷纲；
- 人物状态；
- 伏笔与回收关系。

提前展示多个空章节，会让流程看起来像并行任务管理，而不是连续叙事创作。

这会削弱长篇创作的“当前焦点”：

```text
当前最重要的是下一章，而不是未来五章。
```

### 4.2 对 agent 工作流的影响

当前 StoryForge3 方向是 agent-mode-first。章节生产应由 agent/API 根据状态推进。

如果前端展示五个空章节，agent 的职责边界也会变模糊：

- 是用户点第 2 章让 agent 写？
- 还是 agent 自己决定下一章？
- 第 3-5 章是预生产目标还是空占位？

这会让前端 UI 与后端 agent 流程不一致。

### 4.3 对状态解释的影响

章节状态应来源于产物与运行记录，而不是 UI 推算。

合理真相源：

- `plans/*.json`
- `chapters/*.md`
- `truth/*.json`
- `exports/*`
- `state/chapter_states.json`
- `runs/*.json`
- reconciliation 扫描结果

不合理真相源：

- `current_chapter + 2`
- 固定最少 5 章
- target_chapters 推断可显示章节

## 5. 对前端显示层面的影响

### 5.1 信息层级不清

固定五章模式下，前端没有区分：

- 已写章节；
- 已规划章节；
- 有运行记录章节；
- 空章节；
- 下一章提示。

用户看到的都是“第 N 章卡片”，视觉语义过于相似。

### 5.2 空状态设计缺失

如果一本书只有第 1 章，合理显示应是：

```text
第 1 章  已起草 / 已导出 / 有 Truth

下一章：第 2 章
由 agent 触发生产
```

而不是：

```text
第 1 章
第 2 章 空
第 3 章 空
第 4 章 空
第 5 章 空
```

### 5.3 章节列表与进度条可能不一致

书籍顶部可能显示：

```text
当前章节 1 / 目标章节 100
```

章节列表却显示 5 个章节，会造成明显冲突。

用户会困惑：

- 进度是 1 章还是 5 章？
- 章节卡片是否代表进度？
- 空章节是否计入进度？

### 5.4 容易掩盖数据不一致

如果系统固定展示空卡片，真实的数据异常会被稀释。

例如：

- 第 3 章有 Truth 但无正文；
- 第 4 章有导出但无状态；
- 第 2 章有正文但 run needs_review。

这些本应被突出显示为数据不一致，但如果 UI 本来就展示大量空章节，用户会更难区分“正常空章节”和“异常幽灵章节”。

## 6. 当前较合理的实现方向

当前代码已经采用 reconciliation 驱动章节列表，这是正确方向。

后端 `ChapterReconciler` 会扫描：

```text
chapters/
plans/
truth/
exports/
state/chapter_states.json
runs/
```

并输出每章是否存在：

- 正文；
- 规划；
- Truth；
- 导出；
- 状态；
- 运行记录；
- 是否一致；
- 不一致原因。

前端 `ChapterList` 现在会：

```text
只展示有任意真实产物的章节
并显示一个“下一章由 agent 触发生产”的提示器
```

这是解决固定五章问题的正确基础。

## 7. 仍需优化的问题

### 7.1 顶部文案“真实产物 N 章”可能误导

当前代码显示：

```text
真实产物 {maxChapter} 章
```

但 `maxChapter` 是扫描到的最大章节号，不一定等于真实产物章数。

例如：

```text
第 1 章有正文
第 4 章有残留 truth
```

此时 `maxChapter = 4`，但真实有效章节数不是 4。

建议改成：

```text
已发现章节产物：{chapters.length} 章
最高章节号：第 {maxChapter} 章
```

或：

```text
当前已存在 {validChapterCount} 章，发现 {inconsistent_count} 个异常章节
```

### 7.2 下一章编号不应简单等于 `maxChapter + 1`

当前逻辑：

```ts
const nextChapter = maxChapter + 1;
```

如果存在幽灵章节：

```text
第 1、2 章正常
第 4 章有残留 truth
```

那么系统会提示下一章是第 5 章，但实际应该优先处理第 3 章或修复第 4 章异常。

建议下一章计算规则改为：

```text
找到从第 1 章开始第一个缺失正文且无阻断异常的章节。
```

更具体：

1. 如果存在 inconsistent 章节，先提示“需处理数据不一致”；
2. 如果 1..N 连续章节完整，则下一章是 N+1；
3. 如果中间缺章，则下一章是第一个缺失章节；
4. 如果 maxChapter 来自幽灵产物，不应直接跳过中间章节。

### 7.3 下一章提示器应更像“生产入口说明”，不是章节卡片

当前下一章提示器视觉上接近普通卡片：

```text
第 N 章
由 agent 触发生产
```

建议增强说明：

```text
下一章：第 N 章
尚未产生章节产物。请通过 agent/API 启动生产。
```

并提供只读状态说明，而不是可展开卡片。

### 7.4 卷分组只显示已有章节，可能让卷纲存在感不足

当前按卷分组时，只有该卷已有章节产物才显示卷标题。

这适合“产物视图”，但如果用户想查看卷纲进度，可能希望看到：

```text
第 1 卷：已写 2 / 30 章
```

建议分两个层级：

- 章节产物列表：只显示真实章节；
- 卷进度摘要：显示卷纲目标与已完成数量。

不要把未来章节全部展开成空卡片。

## 8. 改进建议：章节按进度呈现机制

### 8.1 核心原则

章节展示应遵循：

```text
真实产物优先
下一章单点提示
异常优先暴露
不批量展示空章节
```

### 8.2 推荐展示规则

#### 规则一：只展示有产物的章节

有任一产物即展示：

- plan；
- text；
- truth；
- export；
- state；
- run。

这与当前 `hasAnyArtifact()` 一致。

#### 规则二：追加一个下一章提示器

在真实章节之后只显示一个下一章：

```text
下一章：第 N 章
由 agent 触发生产
```

不要预生成多个空章节。

#### 规则三：如果存在数据不一致，优先提示修复

如果 `inconsistent_count > 0`，顶部应显示：

```text
发现 N 个章节产物不一致，请先检查。
```

并在列表中突出异常章节。

#### 规则四：下一章编号由连续有效章节推导

不要用 `maxChapter + 1`。

建议后端或前端新增：

```ts
next_writable_chapter_no
```

其计算方式：

```text
从第 1 章开始，找到第一个没有 text/export 且没有正常完成产物的章节。
```

如果存在中间缺章，优先返回缺章。

#### 规则五：目标章节只作为进度参考，不生成空卡片

`target_chapters` 应用于：

- 顶部进度条；
- 卷进度；
- 目标提示。

不应用于展开空章节。

## 9. 前端实现建议

### 9.1 修改统计显示

当前：

```tsx
真实产物 {maxChapter} 章
```

建议：

```tsx
已发现章节产物 {chapters.length} 章
最高章节号 第 {maxChapter} 章
```

如果有不一致：

```tsx
数据不一致 {inconsistent_count} 章
```

### 9.2 增加 next_chapter 计算字段

推荐后端 reconciliation 返回：

```json
{
  "book_id": "...",
  "chapters": [],
  "inconsistent_count": 0,
  "max_chapter": 2,
  "next_writable_chapter_no": 3
}
```

这样前端不用猜。

### 9.3 调整 NextChapterIndicator 文案

当前：

```tsx
第 {chapterNo} 章
由 agent 触发生产
```

建议：

```text
下一章：第 {chapterNo} 章
尚未产生章节产物。请通过 agent/API 启动生产。
```

若存在不一致章节：

```text
存在数据不一致，建议先处理异常章节后再继续生产。
```

### 9.4 章节卡片增加“产物来源”说明

当前卡片显示：

```text
规划 / 正文 / Truth / 导出
```

建议异常时显示更明确：

- 有 Truth 但无正文；
- 有导出但无状态；
- 有状态但无正文；
- 有 run 但无产物。

当前已有 `inconsistentReasonLabel()`，可以继续扩充。

### 9.5 章节页不要显示运行按钮

当前 `ChapterPipeline` 已说明六个阶段是查看标签，不是运行按钮。这个方向应保持。

建议视觉上进一步弱化“按钮感”：

- 使用 tabs 或步骤条；
- 勾选表示产物存在；
- 当前运行阶段由 RunTrack 点亮；
- 不要让用户误以为可以点击运行。

## 10. 后端实现建议

### 10.1 Reconciler 增加有效章节统计

当前 `max_chapter` 容易被幽灵产物污染。

建议增加：

```python
valid_chapter_count
highest_contiguous_chapter
next_writable_chapter_no
has_blocking_inconsistency
```

含义：

| 字段 | 含义 |
|---|---|
| `valid_chapter_count` | 有正文或正式状态的章节数 |
| `highest_contiguous_chapter` | 从第 1 章开始连续有效的最高章节 |
| `next_writable_chapter_no` | 推荐下一章编号 |
| `has_blocking_inconsistency` | 是否存在阻断继续生产的数据异常 |

### 10.2 区分“产物存在”和“章节有效”

不是所有产物都代表章节有效。

例如：

```text
只有 truth，没有正文
```

应展示为异常，而不是当作“已有章节”。

建议增加状态分类：

```text
valid：有正文或正式状态
partial：只有 plan/run 等部分产物
orphan：truth/export 等孤儿产物
empty：无产物
```

### 10.3 提供 heal/reconcile 策略前置提示

不建议自动删除或修补幽灵章节，但应提供诊断结果。

未来可增加：

```text
/diagnostics/reconcile
/diagnostics/heal-preview
/diagnostics/heal-apply
```

## 11. 产品整体设计建议

### 11.1 章节列表应是“生产账本”，不是“章节目录”

在 agent-mode-first 模型下，章节列表更像生产账本：

```text
这一章有什么产物？
运行到哪一步？
是否一致？
是否可继续？
```

而不是传统目录：

```text
第 1 章
第 2 章
第 3 章
...
```

### 11.2 应突出“当前焦点章节”

用户最关心的是：

- 当前已完成到哪；
- 下一章是哪一章；
- 当前是否有异常阻断。

建议章节页顶部固定展示：

```text
当前连续完成：第 N 章
下一章：第 N+1 章
异常：0 / X
```

### 11.3 空章节不应成为主界面元素

空章节最多作为一个提示器出现，不应批量展示。

这可以显著降低用户的心理负担和误操作概率。

### 11.4 与卷纲结合，但不展开未来章节

卷纲可显示目标：

```text
第 1 卷：已完成 2 / 30 章
```

但不应把 30 个未来章节全部展开。

未来章节应在 agent 实际产生 plan/run 后进入列表。

### 11.5 与 Run Viewer 联动

当 agent 开始生产下一章时：

```text
下一章提示器
  → 转换为真实 ChapterCard
  → 显示 run 状态
  → plan 出现
  → draft 流式出现
  → audit/revise/truth/export 逐步点亮
```

这才是自然的“逐步解锁”。

## 12. 建议实施优先级

### P0：避免误导

1. 不再固定展示 5 章；
2. 顶部文案从“真实产物 maxChapter 章”改成更准确统计；
3. 下一章只显示一个提示器；
4. 若存在数据不一致，优先提示。

### P1：补齐下一章计算

1. Reconciler 返回 `next_writable_chapter_no`；
2. 处理中间缺章；
3. 区分 valid/partial/orphan；
4. 前端使用后端给出的下一章编号。

### P2：卷进度与章节账本结合

1. 显示卷目标进度；
2. 不展开未来空章节；
3. 增加“当前卷生产状态”。

### P3：异常修复工具

1. heal preview；
2. 手动确认修复；
3. 产物来源追踪；
4. RunRecord 与章节产物绑定。

---

## 13. 最终结论

一次性展示五个章节的问题，本质不是简单 UI bug，而是章节列表的真相源和用户心智不匹配。

合理产品模型应是：

```text
已经存在的章节产物才展示为章节卡片；
下一章只作为单个提示器；
章节由 agent/API 生产后自然进入列表；
异常产物优先暴露；
目标章节数只用于进度参考，不用于生成空卡片。
```

当前项目已经开始朝 reconciliation 真相源迁移，这是正确方向。但仍需要优化统计口径、下一章计算和空状态文案，才能让用户真正感受到“写一章，解锁下一章”的自然流程。

一句话建议：

> 章节列表应从“预置章节目录”改为“真实产物账本 + 下一章提示器”，让章节随着 agent 生产逐步出现，而不是提前展示多个空章节。

## 一、P5：Daemon 通知渠道

### 难度评估：⭐⭐ 低（约 2-3 天）

### InkOS 实现参考

InkOS 有完整的 4 通道通知系统：

| 通道 | 实现文件 | 协议 |
|------|----------|------|
| Telegram | `notify/telegram.ts` | Bot API, `sendMessage` |
| 飞书 | `notify/dispatcher.ts` | Webhook |
| 企业微信 | `notify/wechat-work.ts` | Webhook |
| 通用 Webhook | `notify/webhook.ts` | POST + HMAC-SHA256 签名 |

**核心设计**：
- 一个 `dispatcher.ts` 中央分发器，并行发送到所有已配置通道
- 支持事件过滤：`chapter-complete`、`audit-failed`、`pipeline-error`
- 容错：单通道失败只 log 不 throw

### SF3 实现方案

```
新增文件：
├── src/storyforge3/notify/
│   ├── __init__.py
│   ├── dispatcher.py      — 通知分发器
│   ├── telegram.py         — Telegram Bot API
│   ├── feishu.py           — 飞书 Webhook
│   ├── wechat.py           — 企业微信 Webhook
│   └── webhook.py          — 通用 Webhook
└── src/storyforge3/notify/config.py — 通知配置
```

**实现量估算**：
- 每个通道约 50-80 行（HTTP POST 封装）
- dispatcher 约 60 行（并行发送 + 容错）
- config 约 30 行
- 测试每个通道约 30 行 × 4 + dispatcher 30 行 = ~150 行测试
- **总计约 400 行代码 + 150 行测试**

**依赖**：
- httpx（已有）
- 无新依赖

**定时调度入口**：
- 用 Python 标准库的 `asyncio` 或 `sched` 模块
- 或简单的 CLI 入口 `storyforge3 daemon --book xxx --max 5`
- 约 100 行代码

### 结论

**不难做**。InkOS 的实现证明了通知系统可以很轻量。每个通道就是一个 HTTP POST 封装。核心复杂度在 dispatcher 的容错和事件过滤，都是很直接的逻辑。

## 二、前端界面（必须做）

### 难度评估：⭐⭐⭐⭐ 高（约 2-4 周）

### 竞品前端对比

| 项目 | 技术栈 | 界面类型 | 特点 |
|------|--------|----------|------|
| **InkOS** | Ink + React（TUI）/ Vite + React + Hono（Studio） | CLI + TUI + Web | 三种界面共享交互内核 |
| **ANWA** | React 19 + Vite + Plate 编辑器 + Electron | Web + Desktop | "Creative Hub" 统一创作中心 |
| **91Writing** | Vue 3 + Element Plus + WangEditor 5 | Web | 专业富文本编辑器、短篇模块 |
| **51mazi** | Electron + Vue 3 | Desktop | 关系图谱、时间线、地图设计 |

### 方案对比

#### 方案 A：TUI（终端界面）

**参考**：InkOS 的 Ink + React TUI

| 优势 | 劣势 |
|------|------|
| 开发快（1 周） | 非开发者难用 |
| 复用现有 CLI 逻辑 | 无富文本编辑 |
| 不需要浏览器 | 无法展示复杂 UI（图谱、时间线） |

**技术选型**：Python `textual` 或 `rich` 库

#### 方案 B：Web 前端（推荐）

**参考**：ANWA 的 React 架构 / 91Writing 的 Vue 架构

| 优势 | 劣势 |
|------|------|
| 最广泛的用户触达 | 开发量大（2-4 周） |
| 可展示复杂 UI | 前后端分离需要 API 层 |
| 未来可上云部署 | 需要 Node.js 工具链 |

**技术选型建议**：

| 选项 | 前端 | 后端 API | 推荐度 |
|------|------|----------|--------|
| **A. React + FastAPI** | React 19 + Vite + Tailwind | FastAPI 包装现有 Service | ⭐⭐⭐⭐ |
| **B. Vue + FastAPI** | Vue 3 + Element Plus | FastAPI 包装现有 Service | ⭐⭐⭐ |
| C. 全栈 Next.js | Next.js + API Routes | 需要 Node.js 后端 | ⭐⭐ |

**推荐方案 A（React + FastAPI）** 的理由：
1. SF3 已有 11 个 Service Protocol，天然适配 REST API 包装
2. React 生态更大（ANWA、InkOS Studio 都用 React）
3. FastAPI 自动生成 OpenAPI 文档，前端对接方便
4. Plate 编辑器（ANWA 用的）提供专业写作体验

#### 方案 C：Electron 桌面应用

**参考**：ANWA（Electron） / 51mazi（Electron）

| 优势 | 劣势 |
|------|------|
| 原生体验 | 打包体积大（~150MB） |
| 离线可用 | 开发和分发成本高 |
| 可调用本地模型 | 需要 Electron 构建流程 |

**建议**：Phase 2 再考虑。先用 Web 版验证需求。

### SF3 前端实现路线

```
Phase 1（1 周）：API 层
├── src/storyforge3/api/
│   ├── app.py              — FastAPI 应用
│   ├── routes/
│   │   ├── books.py        — CRUD
│   │   ├── chapters.py     — draft/audit/revise/export
│   │   ├── providers.py    — CC-Switch 导入/切换/验证
│   │   ├── world.py        — 世界构建
│   │   ├── characters.py   — 角色管理
│   │   └── daemon.py       — 批量写作
│   └── deps.py             — 依赖注入
└── pyproject.toml 新增 fastapi, uvicorn 依赖

Phase 2（2 周）：React 前端
├── frontend/
│   ├── src/
│   │   ├── pages/
│   │   │   ├── Dashboard.tsx     — 书籍列表 + 状态概览
│   │   │   ├── BookDetail.tsx    — 单书详情（世界/角色/卷/章节）
│   │   │   ├── ChapterEditor.tsx — 章节编辑 + 审计结果 + 修订
│   │   │   ├── ProviderManager.tsx — CC-Switch 导入/切换/验证
│   │   │   └── DaemonControl.tsx  — 批量写作控制面板
│   │   ├── components/          — 共享组件
│   │   └── api/                 — API 客户端
│   └── package.json
```

### 结论

**这是最大的工作量，但也是产品化的关键一步。** ANWA 和 91Writing 都证明了 Web 前端是网文创作工具的标配。SF3 的 11 个 Service Protocol 已经为 API 层做好了准备。

## 三、P6：短篇管线

### 难度评估：⭐⭐⭐ 中（约 1 周）

### InkOS 实现参考

InkOS 的短篇管线是 7 阶段 6-Agent 系统：

```
OutlineAgent → OutlineReviewer → OutlineReviser → WriterAgent
→ DraftReviewer → DraftReviser → PackagingAgent
```

**输出**：完整草稿 + 销售包装（梗概/卖点/封面提示词）

### 91Writing 实现参考

91Writing 有成熟的短篇模块：
- 6 个专业模板（都市/玄幻/言情/悬疑/科幻/通用）
- Prompt 选择器 + 变量自动填充
- 续写功能 + 优化功能
- 双标签界面（短文写作 + 短篇小说）

### SF3 实现方案

```
新增文件：
├── src/storyforge3/services/short_fiction_service.py
├── src/storyforge3/services/packaging_service.py
└── src/storyforge3/prompts/short_fiction/ (模板)
```

**与长篇的区别**：
- 无卷纲规划，直接从方向到大纲
- 无记忆数据库（短篇不需要跨章 truth）
- 无 Daemon（短篇一次性完成）
- 增加"销售包装"阶段（梗概、卖点、封面提示词）

**实现量估算**：
- ShortFictionService 约 200 行（大纲 → 批量起草 → 审核 → 包装）
- PackagingService 约 100 行
- 模板约 5-6 个
- 测试约 200 行
- **总计约 500 行代码 + 200 行测试**

### 结论

**中等难度**。核心逻辑和长篇管线类似，但简化了很多（无卷、无 truth、无 daemon）。InkOS 和 91Writing 的实现可以直接参考。

## 四、P7：同人模式

### 难度评估：⭐⭐⭐ 中（约 1 周）

### InkOS 实现参考

InkOS 有 4 种同人模式：

| 模式 | 说明 | 审计严格度 |
|------|------|------------|
| canon | 原作向 | 角色/世界/事件 全 critical |
| au | 平行宇宙 | 世界/事件 放松为 info |
| ooc | 角色偏离 | 角色还原度降为 info |
| cp | 关系向 | 关系动态 warning |

**核心组件**：
- `FanficCanonImporter`：从原著提取世界规则、角色档案、事件时间线、能力体系、写作风格
- 4 个同人专属审计维度（34-37）：角色还原度、世界规则遵守、关系动态、正典事件一致性
- 按模式调整审计严重度

### SF3 实现方案

```
新增文件：
├── src/storyforge3/fanfic/
│   ├── __init__.py
│   ├── canon_importer.py    — 原著提取
│   ├── modes.py             — 4 种模式定义
│   └── audit_dimensions.py — 4 个同人审计维度
└── src/storyforge3/services/fanfic_service.py
```

**实现量估算**：
- canon_importer 约 150 行（用 LLM 提取结构化 canon）
- modes.py 约 50 行（模式 → 审计严格度映射）
- audit_dimensions 约 100 行（4 个维度）
- fanfic_service 约 150 行（导入 → 提取 → 创作 → 审计）
- 测试约 200 行
- **总计约 450 行代码 + 200 行测试**

### 结论

**中等难度**。核心创新在 canon 提取和模式敏感的审计。InkOS 的模式→严重度映射是很好的设计模式。

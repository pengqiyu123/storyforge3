### 关键发现

**91Writing 不能作为架构参考**。代码质量过低（纯 JS、万行 god component、零测试），只借鉴其小 writer 组件（200-250 行）的粒度思路。

**ANWA 和 InkOS 是同级参考**（均为 B+），各有所长，应择优组合：

| 方面 | 从 ANWA 借鉴 | 从 InkOS 借鉴 |
|------|-------------|--------------|
| 状态管理 | 精简独立 store 模式（4 个小 store > 1 个大 store） | Zustand slice 组合模式（当 store 需要分片时） |
| API 客户端 | axios 全局拦截器 + 统一错误类型 | SSE (Server-Sent Events) 实时推送架构 |
| 类型系统 | shared/ 跨前后端共享类型 + Zod 运行时校验 | hash 路由（无需服务器配置）+ 自定义 ApiError |
| 安全 | — | 路径遍历防护 (isSafeBookId) + 事件类型化 |
| 编辑器 | Plate.js 集成模式（ANWA 已验证可用） | — |
| 反面教训 | NovelEdit.tsx 2669 行 → 组件必须拆分 | server.ts 3666 行 → API 必须按路由拆文件 |

## 二、技术选型决策：React 19 + FastAPI

### 为什么不是 Vue 3

| 考量 | React 19 | Vue 3 |
|------|----------|-------|
| 参考项目质量 | 两个 B+ 级参考可借鉴 | 唯一参考 D+，无可借鉴架构 |
| 编辑器选择 | Plate.js（ANWA 已验证） | WangEditor（功能弱、维护差） |
| UI 组件库 | shadcn/ui（两个参考都用，质量高） | Element Plus（成熟但写作工具生态弱） |
| 状态管理 | Zustand（两个参考验证） | Pinia（91Writing 用成 841 行 god store） |
| 类型安全 | 两个参考均 TypeScript，0.3% any | 零参考提供 TypeScript 最佳实践 |
| SSE 支持 | React 生态成熟（InkOS 已验证） | 需要自行探索 |
| **结论** | **✅ 选定** | ❌ 风险过高 |

### 为什么不是 Next.js / Electron（Phase 1）

- **Next.js**：强制 Node.js 后端，与 SF3 的 Python 引擎冲突，需要额外维护一套 Node 服务端
- **Electron**：打包 150MB+，Phase 1 应先用 Web 版验证需求，Phase 2 再考虑 Tauri（更轻量）
- **推荐路线**：Vite + React SPA + FastAPI 后端 → 未来可包装为 Tauri 桌面应用

### 最终技术栈

```
前端：React 19 + Vite + TypeScript + Tailwind CSS + shadcn/ui + Zustand
后端：FastAPI (Python, 包装 SF3 现有 11 个 Service Protocol)
实时通信：SSE (Server-Sent Events, 参考 InkOS)
编辑器：Plate.js (参考 ANWA, Phase 2 引入)
API 校验：Pydantic (后端, 已有) + Zod (前端, 参考 ANWA)
```

### 设计原则

1. **按功能边界拆分，不按行数拆分** — 每个文件/组件/模块只负责一个功能边界。行数是气味指标不是硬限：200 行内完成一个功能边界是理想状态，但当一个功能边界本身逻辑复杂时允许灵活增长。真正的红线是"一个文件里混了两个以上不相关的功能职责"
2. **反面教训的红线** — InkOS server.ts 3666 行（路由+业务+校验+I/O 混杂）、ANWA NovelEdit.tsx 2669 行（50+ state variable 混杂）、91Writing Writer.vue 11205 行（编辑+章节+角色+世界观+AI 全塞一个文件）— 这些不是"太长了"的问题，是**功能边界彻底丧失**
3. **API 层不包含业务逻辑** — 路由只做参数校验 + 调用 Service + 返回结果
4. **前端不调用 Service** — 全部通过 FastAPI HTTP API，前端不直接 import Python
5. **类型对齐靠 OpenAPI** — Python 和 TypeScript 类型分别维护，通过 FastAPI 自动生成的 OpenAPI schema 对齐

## 四、开发规范（防止 AI 偏离）

### 4.1 后端 API 规范

```python
# ✅ 正确：路由只做参数校验 + 调用 Service
@router.post("/books/{book_id}/chapters/{chapter_no}/draft")
async def draft_chapter(
    book_id: str,
    chapter_no: int,
    service: ChapterService = Depends(get_chapter_service),
):
    result = await service.draft(book_id, chapter_no)
    return ChapterDraftResponse.from_result(result)

# ❌ 错误：路由包含业务逻辑
@router.post("/books/{book_id}/chapters/{chapter_no}/draft")
async def draft_chapter(book_id: str, chapter_no: int):
    # 不要在路由里写 LLM 调用、状态管理、truth 操作
    ...
```

**API 响应格式（统一信封）**：

```python
# 成功
{"ok": true, "data": {...}, "error": null}

# 失败
{"ok": false, "data": null, "error": {"code": "CHAPTER_NOT_FOUND", "message": "..."}}

# 分页
{"ok": true, "data": [...], "error": null, "meta": {"total": 100, "page": 1, "limit": 20}}
```

**错误码规范**：

| HTTP 状态 | code 字段 | 含义 |
|-----------|----------|------|
| 400 | INVALID_PARAMETER | 请求参数校验失败 |
| 404 | BOOK_NOT_FOUND / CHAPTER_NOT_FOUND | 资源不存在 |
| 409 | STATE_CONFLICT | 状态机不允许的操作 |
| 422 | AUDIT_FAILED | 审计未通过（返回审计详情） |
| 500 | INTERNAL_ERROR | 服务端异常 |

### 4.2 前端组件规范

```
功能边界拆分规则（按职责划分，不按行数机械切割）：

  "一个文件只做一件事"的判断标准：
  - 能用一句话说清这个文件的职责 → 边界清晰
  - 需要两句话以上 → 拆分
  - 例子：
    ✅ "处理章节草稿的 API 路由" — 一个文件，清晰
    ✅ "展示章节审计结果的面板组件" — 一个文件，清晰
    ❌ "处理章节相关的所有操作" — 模糊，可能包含草稿/审计/修订/导出多个功能
    ❌ "写作页面的所有逻辑" — 模糊，ANWA 的 NovelEdit 就死在这里

  灵活度：
  - 功能边界内的代码量不设硬限。一个路由如果逻辑复杂到 350 行，但职责仍然是单一的，可以接受
  - 当一个文件超过 200 行时，自觉检查：是否混入了第二个功能边界？如果是 → 拆
  - 当一个文件超过 500 行时，无论是否单一职责，必须拆分（说明这个功能边界本身需要子模块化）

  组件层级：
  - 页面组件 (pages/)：布局 + 组合子组件，不做具体逻辑
  - 业务组件 (components/)：单一职责，按功能领域分组
  - UI 组件 (components/ui/)：纯展示、无业务逻辑

状态管理规则：
- 服务器状态 → React Query (TanStack Query)
- UI 状态（面板开关、侧边栏）→ Zustand uiStore
- 编辑器状态 → Zustand editorStore
- URL 状态 → hash 路由参数
- 表单状态 → React Hook Form（如需复杂表单）
- ❌ 禁止：将 API 返回数据存入 Zustand（用 React Query 的 cache）

API 调用规则：
- 所有 API 调用通过 api/ 层的 React Query hooks
- ❌ 禁止：在组件里直接写 fetch/axios 调用
- ❌ 禁止：在组件里写业务逻辑（提取到 hooks 或 utils）

命名规范：
- 组件文件：PascalCase.tsx
- Hook 文件：camelCase.ts，导出函数 use 开头
- Store 文件：camelCase.ts，导出 use 开头
- API 文件：camelCase.ts，按领域分组
- 类型文件：camelCase.ts，按领域分组
```


### 4.5 禁止清单（红线）

```
后端：
❌ 一个路由文件混入多个不相关的功能职责
❌ 在路由里直接调用 LLM / 操作 truth / 修改状态
❌ 新增 Python 依赖不经 pyproject.toml
❌ API 返回裸字符串错误（必须用统一信封）
❌ 单个文件超过 500 行（说明功能边界需要子模块化）

前端：
❌ 一个组件承担多个不相关的功能职责（91Writing Writer.vue 的教训）
❌ 在组件里直接调用 axios/fetch
❌ 用 any 类型（用 unknown + 类型守卫）
❌ console.log 提交到代码中（91Writing 的教训）
❌ 将 API 数据存入 Zustand（用 React Query cache）
❌ 单个文件超过 500 行（说明功能边界需要子模块化）

共同红线：
❌ 功能边界丧失 = 混了两个以上不相关的职责 → 必须拆分
  判断方法：能用一句话说清职责 → OK，需要两句话以上 → 拆
```

## 七、风险与缓解

| 风险 | 概率 | 缓解 |
|------|------|------|
| AI 生成 god component | 高 | 红线规范 + 每次提交前检查行数 |
| API 层泄露业务逻辑 | 中 | 路由只调 Service，禁止直接操作 state/truth/LLM |

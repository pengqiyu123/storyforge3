## StoryForge3 质量评估结论

总体评级：**B+ / A- 候选**

StoryForge3 的核心架构已经比较成熟：服务层边界清晰、后端测试面较广、Web 工作台已形成闭环、Fail-Closed 和 Truth 管理意识强。  
但离“可稳定交付给真实作者长期使用”仍有几个关键风险：**本地 API 安全边界、真实 dogfood 证据不足、长任务体验、性能/资源可观测性、部分输入路径校验不足**。

本次评估基于我只读检查的当前代码与文档，包括 [CLAUDE.md](file:///d:/python/Novel/storyforge3/CLAUDE.md)、[AGENTS.md](file:///d:/python/Novel/storyforge3/AGENTS.md)、[README.md](file:///d:/python/Novel/storyforge3/README.md)、[current.md](file:///d:/python/Novel/storyforge3/docs/current.md)、后端核心文件、Web 组件、Tauri 进程管理与测试目录。

## 1. 代码质量

### 优点

- **架构分层清楚**：服务协议集中在 [protocols.py](file:///d:/python/Novel/storyforge3/src/storyforge3/services/protocols.py#L1-L339)，API/Web/MCP/Tauri 都围绕服务层消费。
- **数据模型集中**：主要 dataclass 和枚举集中在 [models.py](file:///d:/python/Novel/storyforge3/src/storyforge3/models.py#L1-L359)，便于跨层对齐。
- **存储写入较谨慎**：基础 JSON/text 写入使用临时文件替换，见 [storage.py](file:///d:/python/Novel/storyforge3/src/storyforge3/storage.py#L60-L83)。
- **核心工作流有明确 fail-closed 语义**：章节管线在 [workflow.py](file:///d:/python/Novel/storyforge3/src/storyforge3/workflow.py#L43-L260) 中对 plan、draft、audit、truth、export 失败均有记录或进入 `needs_review`。
- **注释风格总体克制**：多数注释解释业务边界和设计意图，而不是重复代码。

### 问题与风险

#### P1：部分模块职责偏重，后续维护成本上升

[workflow.py](file:///d:/python/Novel/storyforge3/src/storyforge3/workflow.py) 和 [chapter_service.py](file:///d:/python/Novel/storyforge3/src/storyforge3/services/chapter_service.py) 承担了章节计划、起草、修订、审计、上下文、truth、快照、导出等多种职责。短期可接受，但继续扩展会导致回归风险上升。

建议：

- 把 `ChapterWorkflow` 拆成更小的协作者：
  - `ChapterPlanningRunner`
  - `DraftRunner`
  - `RevisionRunner`
  - `TruthCommitRunner`
  - `PipelineDiagnosticsWriter`
- 先拆“修订”和“日志/诊断”，因为这两块最容易变复杂。

#### P1：API 依赖注入每次请求重建服务，性能和状态一致性一般

[deps.py](file:///d:/python/Novel/storyforge3/src/storyforge3/api/deps.py#L31-L157) 中多数依赖按请求创建，`ChapterService`、`TruthStore`、`LLMService`、`PipelineLogger` 等都可能频繁初始化。对小项目没问题，但长任务和桌面常驻场景会增加开销。

建议：

- 将纯配置、PromptRegistry、ProviderConfigManager、LLMService 等做应用级缓存。
- 对持久化服务保留轻量实例，但共享底层只读配置。
- 加入启动期健康检查结果缓存，避免 UI 每次操作都触发重复探测。

#### P2：部分异常处理过宽

搜索到多处 `except Exception` / `except BaseException`，例如 [workflow.py](file:///d:/python/Novel/storyforge3/src/storyforge3/workflow.py)、[provider_config.py](file:///d:/python/Novel/storyforge3/src/storyforge3/llm/provider_config.py#L84-L103)、[workspace_service.py](file:///d:/python/Novel/storyforge3/src/storyforge3/services/workspace_service.py#L40-L63)。很多是为了日志和清理，合理；但部分会削弱诊断精度。

建议：

- 对业务边界异常使用明确类型：`LLMCallError`、`TruthExtractionError`、`ExportFormatError`、`WorkspaceRestoreError`。
- API 层统一把未知异常转成 `INTERNAL_ERROR`，但日志保留 traceback。
- 保留 `BaseException` 只用于临时文件清理场景。

建议：

- 立刻执行 3 次真实 dogfood：
  1. 新书第 1 章。
  2. 连续第 2-3 章。
  3. 存量书下一章。
- 每次记录：
  - plan/draft/audit/revise/truth/export 耗时。
  - 审计误判/漏判。
  - 作者是否需要绕过系统。
  - LLM 成本和失败原因。
- 把结论整理成 `docs/dogfood-runs/` 下的运行记录。

#### P1：Web UI 功能覆盖虽广，但“下一步引导”仍弱

[BookDetailPage.tsx](file:///d:/python/Novel/storyforge3/web/src/pages/BookDetailPage.tsx#L84-L134) 已有世界观、角色、卷、章节、truth、快照等 tab，但概览只显示“下一步：进入章节管线”，对新用户不够明确。

建议：

- 在概览页增加“创作准备检查清单”：
  - 是否已有世界观。
  - 是否已有主角。
  - 是否已有卷纲。
  - 下一章状态。
  - Provider 是否连通。
- 每项直接跳转到对应 tab。
- 对缺失项显示“推荐下一步”。

#### P1：全流程按钮的风险提示不足

[ChapterPipeline.tsx](file:///d:/python/Novel/storyforge3/web/src/components/chapters/ChapterPipeline.tsx#L243-L247) 有“运行全流程”，但这是高成本、高耗时、高状态变更操作。当前 UI 没看到强确认或预算提示。

建议：

- 点击“运行全流程”前弹出确认：
  - 预计会调用 LLM。
  - 可能耗时数分钟。
  - 会写入章节、truth、导出文件。
- 显示当前 provider/model。
- 提供“只运行到草稿”“运行到审计”“完整运行”三个选项。

虽然 [LLMCallRecord](file:///d:/python/Novel/storyforge3/src/storyforge3/models.py#L103-L115) 有 tokens、latency、success，但用户侧看不到完整性能报告。

### 已做得好的地方

- 工作区恢复有 zip slip 防护，见 [workspace_service.py](file:///d:/python/Novel/storyforge3/src/storyforge3/services/workspace_service.py#L128-L139)。

### 关键风险

#### P0：FastAPI CORS 完全开放，且本地 API 无鉴权

[app.py](file:///d:/python/Novel/storyforge3/src/storyforge3/api/app.py#L27-L32) 使用：

```python
allow_origins=["*"]
allow_methods=["*"]
allow_headers=["*"]
```

如果服务绑定在本机端口，恶意网页仍可能诱导浏览器访问本地 API，执行创建、导出、恢复、provider 操作等请求。即使是本地桌面应用，也应加本地访问保护。

建议：

- 默认只允许：
  - `http://localhost:5173`
  - `http://127.0.0.1:5173`
  - Tauri origin
- 增加本地 CSRF token：
  - 后端启动生成随机 token。
  - 前端请求带 `X-SF3-Token`。
  - 所有写操作校验 token。
- 或至少限制写接口只接受来自 Tauri/本地 UI 的 token。
- 生产桌面模式不要 `allow_origins=["*"]`。

#### P1：`book_id` 路径输入缺少统一校验

[StoragePaths.book_dir](file:///d:/python/Novel/storyforge3/src/storyforge3/storage.py#L14-L16) 直接拼接 `books_root / book_id`。部分下载/恢复路径做了防护，但 book_id 是跨 API、MCP、CLI 的核心输入，建议统一校验，避免 `../`、绝对路径、特殊字符造成越界风险。

建议：

- 增加 `validate_book_id(book_id)`：
  - 只允许 `[a-zA-Z0-9_-]` 或项目定义的 slug。
  - 禁止 `/`、`\`、`..`、空值、控制字符。
- 在 API 参数、MCP tool、Service 入口统一调用。
- 对已有中文书名，应区分 `book_id` 和 `title`：title 可中文，book_id 应是安全 slug。

#### P1：Provider 验证失败信息可能包含敏感内容

[provider_config.py](file:///d:/python/Novel/storyforge3/src/storyforge3/llm/provider_config.py#L84-L103) 会把 `str(exc)` 写入 probe message。某些 HTTP 库或 provider 错误可能回显 URL、header、key 片段。

建议：

- 写入前统一调用 `redact_secrets(message)`。
- 脱敏：
  - API key。
  - bearer token。
  - URL query 中的 `key=`。
  - Authorization header。
- 日志和 API 返回都用脱敏版本。

## 最终判断

StoryForge3 不是“代码能跑但产品松散”的原型，而是已经有清晰工程纪律的中后期项目。当前最值得投入的不是继续堆功能，而是：

1. **安全边界补强**；
2. **真实作者 dogfood**；
3. **长任务体验与诊断可视化**；
4. **核心大模块拆分**。

如果这四项完成，项目质量可以从现在的 **B+ / A- 候选** 提升到更稳定的 **A 级可用产品基线**。

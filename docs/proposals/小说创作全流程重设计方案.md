# 小说创作全流程重设计与优化方案

> 适用项目：StoryForge3  
> 存储位置：项目根目录  
> 目标：重新设计并规范小说创作从初始构思到最终定稿、导出、复盘的全生命周期流程，修正当前流程衔接、状态流转、持久化和人工决策中的逻辑漏洞。

---

## 1. 总体结论

StoryForge3 当前已经具备章节规划、起草、审计、修订、truth 提取、导出、Web UI、MCP 和桌面壳等能力，但流程设计仍偏“功能堆叠”，还没有形成足够严格的全生命周期生产体系。

当前最需要优化的不是继续增加单点能力，而是建立统一的 **创作流程操作系统**：

```text
构思输入
  -> 建书与基础设定
  -> 世界观/角色/卷纲准备
  -> 章节规划
  -> 正文起草
  -> 长度与格式整理
  -> 质量审计
  -> 多轮修订
  -> 人工批准
  -> Truth 提交
  -> 平台导出
  -> 运行复盘与下一章准备
```

该流程必须同时支持两种使用方式：

1. **前端手动模式**：作者逐步点击、查看、编辑、确认。
2. **Agent 自动模式**：自动导演或外部 Agent 按统一动作接口执行、暂停、恢复、回滚。

核心设计原则：

- 所有关键产物必须持久化，不能只存在前端内存。
- 每个阶段必须有标准输入、标准输出和明确状态推进规则。
- 长任务必须有运行记录、阶段进度、失败原因和恢复点。
- AI 只负责生成和建议，最终作品批准权属于作者。
- Truth 是批准后的事实层，不应在未批准草稿上随意提交。
- 导出必须以已批准内容和已提交 truth 为前置条件。

## 2. 当前设计主要问题

### 2.1 阶段产物不完全持久化

正文、世界观、角色、truth、导出文件已经进入受控存储，但章节规划曾长期只存在前端内存状态中，刷新后消失。类似问题说明：流程中的每个阶段产物都必须被视为正式数据，而不是 UI 临时结果。

需要持久化的产物包括：

- 书籍构思；
- 世界观；
- 角色；
- 卷纲；
- 章节规划；
- 草稿版本；
- 审计报告；
- 修订建议；
- 修订 diff；
- 批准记录；
- truth delta；
- 导出记录；
- pipeline run 日志。

### 2.2 状态含义混杂

当前 `ChapterStatus` 同时承载“产物状态”和“流程状态”。例如：

- `PLANNED` 表示有规划产物；
- `DRAFTED` 表示有正文草稿；
- `NEEDS_REVIEW` 既可能是审计失败、truth 失败，也可能是人工确认缺失；
- 长任务运行中的 `planning/drafting/auditing` 进度主要依赖事件流，不是正式状态。

建议拆分：

1. **章节产物状态**：章节当前保存到哪一步。
2. **运行实例状态**：某一次 pipeline run 正在执行哪一步、是否失败、是否可恢复。

### 2.3 Service、Workflow、API、MCP 的职责边界需要统一

当前已有 Service Protocol 和 ChapterWorkflow，但仍存在：

- 单步按钮调用走 `ChapterService`；
- 全流程运行走 `ChapterWorkflow`；
- API / MCP / Web 各自组合调用；
- 动作元信息、确认点、幂等、风险级别没有统一定义。

建议引入统一 Action 层，形成：

```text
Frontend / MCP / CLI / AutoDirector
  -> Action Adapter
  -> Action Module
  -> Domain Service
  -> Storage / LLM / Truth / Export
```

### 2.4 审计、修订、批准、truth、导出之间的门禁不够显式

理想顺序应为：

```text
草稿 -> 审计 -> 修订 -> 再审计 -> 作者批准 -> truth 提交 -> 导出
```

不能出现：

- 未批准草稿直接 truth 入库；
- truth 缺失但导出成功；
- 审计阻断仍自动批准；
- 修订后不再审计；
- 导出使用的正文版本与批准版本不一致。

### 2.5 缺少统一异常恢复机制

当前异常处理偏分散。需要对以下情况给出标准策略：

- LLM 超时；
- provider 失败；
- 流式中断；
- 审计阻断；
- 修订多轮失败；
- 人工拒绝；
- truth 提取失败；
- 导出失败；
- 存储写入失败；
- 页面刷新或后端重启。

## 3. 设计目标

### 3.1 产品目标

- 支持作者从一句灵感到完整章节交付。
- 支持章节续写、从零开书、自动导演三种核心场景。
- 支持复杂世界观、长篇连续性和跨章 truth 召回。
- 让作者始终知道当前处于哪一步、下一步做什么、失败后如何恢复。

### 3.2 工程目标

- 每个阶段是可测试、可重试、可恢复的独立动作。
- 所有关键产物原子落盘。
- API、Web、MCP、Agent 共享同一套动作语义。
- 长任务通过 SSE / run record 提供可观察性。
- 状态流转可审计，禁止非法倒退和隐式覆盖。

### 3.3 运营目标

- dogfood 可记录每一步耗时、质量、错误、误判和人工干预。
- 后续 Phase 10B AutoDirector 可直接复用该流程。
- 可形成稳定的创作质量指标：成功率、误判率、修订通过率、truth 漏提率、导出成功率。

## 4. 核心角色与权责

| 角色 | 权责 |
|---|---|
| 作者 | 提供构思、确认设定、编辑正文、最终批准章节。 |
| AI Planner | 生成世界观、角色、卷纲和章节规划。 |
| AI Writer | 根据规划和上下文生成正文草稿。 |
| Mechanical Auditor | 执行确定性规则审计，输出阻断、警告和信息。 |
| LLM Auditor | 补充语义、连续性、风格和剧情质量审计。 |
| AI Reviser | 根据审计结果执行指定模式修订。 |
| Truth Manager | 提取、保存和检索跨章事实。 |
| Exporter | 按平台规则生成导出文件。 |
| Pipeline Orchestrator | 编排阶段、记录运行、发出事件、处理恢复。 |
| Agent / AutoDirector | 根据动作元信息自动调用流程，不能绕过高风险确认。 |
| PM / 维护者 | 定义验收标准、审查 dogfood 结果、决定阶段推进。 |

## 6. 状态模型重设计

### 6.1 章节产物状态

建议章节状态保持粗粒度、可恢复：

```text
EMPTY
  -> PLANNED
  -> DRAFTED
  -> AUDITED
  -> NEEDS_REVISION
  -> REVISED
  -> AUDITED
  -> APPROVED
  -> TRUTH_COMMITTED
  -> EXPORTED
```

考虑到现有模型已有 `NEEDS_REVIEW`，建议保留作为异常汇合状态：

```text
任何阶段失败且不能自动恢复 -> NEEDS_REVIEW
```

推荐补充或内部标记：

- `TRUTH_COMMITTED`：truth 已成功提交，导出前置条件满足。
- 如果短期不新增 enum，可用 `APPROVED + truth exists` 表示，但文档和代码必须明确。

### 6.2 运行实例状态

长任务不应把“运行中”直接塞进章节状态，应由 `PipelineRunRecord` 表示：

```text
PENDING
  -> RUNNING
  -> WAITING_FOR_HUMAN
  -> COMPLETED
  -> FAILED
  -> CANCELLED
  -> RESUMABLE
```

每个 run 记录：

- `run_id`；
- `book_id`；
- `chapter_no`；
- `current_stage`；
- `started_at`；
- `updated_at`；
- `stage_results`；
- `llm_calls`；
- `error_code`；
- `resume_from`。

### 6.3 状态推进规则

| 当前状态 | 可进入状态 | 禁止行为 |
|---|---|---|
| EMPTY | PLANNED | 不能直接导出。 |
| PLANNED | DRAFTED、NEEDS_REVIEW | 不能提交 truth。 |
| DRAFTED | AUDITED、NEEDS_REVIEW | 不能直接导出。 |
| AUDITED | APPROVED、NEEDS_REVISION、NEEDS_REVIEW | 阻断问题未处理不能批准。 |
| NEEDS_REVISION | REVISED、NEEDS_REVIEW | 不能直接导出。 |
| REVISED | AUDITED、NEEDS_REVIEW | 修订后必须再审计。 |
| APPROVED | TRUTH_COMMITTED、NEEDS_REVIEW | 未提交 truth 不应导出。 |
| TRUTH_COMMITTED | EXPORTED | 导出必须绑定批准正文 hash。 |
| EXPORTED | 无或重新规划分支 | 默认不可覆盖，需显式新版本。 |
| NEEDS_REVIEW | 人工选择恢复点 | 禁止自动无确认继续。 |

## 7. 全流程阶段设计

## 阶段 0：构思与建书

### 任务清单

- 输入一句灵感、题材、目标平台、目标章节数、章节字数。
- 生成或确认 `BookConfig`。
- 创建书籍目录和基础元数据。
- 初始化运行记录。

### 输入

- `IdeaBrief`；
- 用户选择的 genre/platform；
- 可选参考作品、禁区、风格要求。

### 输出

- `BookMeta`；
- `IdeaBrief`；
- 初始 `PipelineRunRecord`。

### 决策节点

- 构思是否足够明确？
- 题材与平台是否匹配？
- 是否需要人工补充卖点或禁区？

### 异常处理

- 输入过短：要求用户补充。
- 书名冲突：生成安全 slug 或让用户确认。
- 创建失败：不写半成品，返回明确错误。

---

## 阶段 1：世界观、角色、卷纲准备

### 任务清单

- 生成世界观。
- 生成主要角色。
- 生成第一卷或全书卷纲。
- 检查世界观、角色、卷纲是否互相一致。
- 进入人工确认点。

### 输入

- `BookMeta`；
- `IdeaBrief`；
- 平台要求；
- 可选参考资料。

### 输出

- `WorldConfig`；
- `CharacterSet`；
- `VolumeOutline`；
- `SetupAuditReport`。

### 参与角色

- AI Planner；
- 作者；
- Mechanical Auditor；
- Agent 可自动执行，但不能跳过确认点。

### 判断标准

- 世界规则有边界，不自相矛盾。
- 主角目标明确。
- 主要角色不只是标签。
- 卷纲具备阶段目标、矛盾升级和章节分配。

### 异常处理

- 世界观空泛：退回重生成或要求用户补充。
- 角色脸谱化：进入角色重写动作。
- 卷纲与目标章节数不匹配：自动重新分配。

---

## 阶段 2：章节规划

### 任务清单

- 读取世界观、角色、卷纲、前文、truth。
- 生成本章目标、冲突、场景顺序、必须保留、必须避免。
- 持久化 `ChapterPlanState`。
- 推进章节状态到 `PLANNED`。

### 输入

- `book_id`；
- `chapter_no`；
- `WorldConfig`；
- `CharacterSet`；
- `VolumeOutline`；
- 前章 truth；
- 用户备注。

### 输出

- `ChapterPlanState`。

### 关键要求

- 规划必须后端落盘。
- `draft()` 必须优先复用已保存规划。
- 浏览器刷新、后端重启后必须能恢复规划。
- 重新规划是覆盖操作，应有确认或版本记录。

### 判断标准

- 本章目标明确。
- 与卷纲一致。
- 与前章 truth 不冲突。
- 有可执行场景，不是抽象建议。

### 异常处理

- LLM 超时：保留 run record，允许重试。
- 规划质量低：进入重规划。
- 存储失败：不得推进状态。

---

## 阶段 3：内容起草

### 任务清单

- 加载 `ChapterPlanState`。
- 组装上下文包。
- 召回 truth。
- 执行正文生成。
- 长文使用 chunked generation。
- 流式发布进度。
- 保存 `DraftVersion`。
- 推进状态到 `DRAFTED`。

### 输入

- `ChapterPlanState`；
- 世界观和角色；
- 前章尾部；
- 相关 truth；
- 风格约束；
- 目标字数。

### 输出

- `DraftVersion`；
- LLM call records；
- chunk progress events。

### 判断标准

- 字数在目标区间内。
- 没有系统提示词泄漏。
- 章节有事件推进。
- 角色对话有区分度。
- 与 plan 主要目标一致。

### 异常处理

- provider 超时：保留已完成 chunk，允许从 chunk 边界重试。
- 输出过短：进入长度补全。
- 输出包含工程术语：进入审计阻断或自动清理。
- 用户取消：标记 run 为 `CANCELLED`，草稿不覆盖已有批准版本。

---

## 阶段 4：整理与标准化

### 任务清单

- 检查长度。
- 修正常见格式问题。
- 移除 Markdown 包装或多余解释。
- 保留正文版本 hash。

### 输入

- `DraftVersion`。

### 输出

- `SettledDraftVersion`。

### 判断标准

- 正文可直接进入审计。
- 不改变剧情事实。
- 不产生新设定。

### 异常处理

- 标准化失败：保留原草稿，标记 `NEEDS_REVIEW`。

---

## 阶段 5：质量审计

### 任务清单

- 执行 36 条机械审计规则。
- 可选执行 LLM 审计。
- 聚合阻断、警告、信息。
- 输出 `AuditReport`。
- 根据结果进入批准或修订。

### 输入

- 整理后正文；
- 平台规则；
- 世界观；
- 角色；
- truth；
- 风格契约。

### 输出

- `AuditReport`。

### 判断标准

- blocking issue = 0 才可进入批准。
- warning 可由作者决定是否处理。
- LLM 审计不能覆盖机械审计阻断，只能补充。

### 异常处理

- 机械审计异常：视为 P0，不能继续。
- LLM 审计失败：可降级为仅机械审计，但必须记录。
- 审计误判：允许人工标记 false positive，进入规则优化 backlog。

---

## 阶段 6：多轮修订

### 任务清单

- 根据审计结果推荐修订模式。
- 生成修订计划。
- 执行修订。
- 保存 before snapshot。
- 生成 `RevisionDiff`。
- 修订后重新审计。
- 最多执行限定轮次。

### 输入

- 正文版本；
- `AuditReport`；
- 修订模式；
- 用户备注。

### 输出

- `RevisionDiff`；
- 新正文版本；
- 新 `AuditReport`。

### 修订模式

| 模式 | 适用场景 |
|---|---|
| polish | 文风润色、节奏改善。 |
| spot_fix | 局部规则命中。 |
| anti_detect | AI 腔、模板化表达。 |
| surgical | 精准替换，不动整体结构。 |
| rework | 大面积失败，需要重写。 |

### 判断标准

- 修订后 blocking issue 减少。
- 不引入新设定冲突。
- 不破坏章节核心目标。
- 修订 diff 可解释。

### 异常处理

- 修订后更差：回滚到 before snapshot。
- 多轮仍不通过：进入 `NEEDS_REVIEW`。
- 用户拒绝修订：回到人工编辑。

---

## 阶段 7：最终批准

### 任务清单

- 展示正文、审计、diff、truth 预览。
- 作者确认是否批准。
- 保存 `ApprovalRecord`。
- 锁定批准正文 hash。
- 推进状态到 `APPROVED`。

### 输入

- 当前正文版本；
- 最近审计报告；
- 修订 diff；
- 用户确认。

### 输出

- `ApprovalRecord`。

### 判断标准

- 无 blocking issue。
- 作者确认可进入事实层。
- 正文 hash 与展示版本一致。

### 异常处理

- 作者拒绝：进入人工编辑或重新修订。
- 正文在批准前被修改：要求重新审计。
- 审计报告过期：要求重新审计。

---

## 阶段 8：Truth 提交

### 任务清单

- 从批准正文提取 truth。
- 与前章 truth 合并。
- 检查事实冲突。
- 保存 SQLite 和 JSON 备份。
- 推进到 `TRUTH_COMMITTED` 或标记 `APPROVED_WITH_TRUTH_PENDING`。

### 输入

- 批准正文；
- `ApprovalRecord`；
- 前章 truth；
- 世界观和角色。

### 输出

- `TruthDelta`；
- 更新后的 truth store。

### 判断标准

- 关键不可逆事实无遗漏。
- 角色关系变化被记录。
- 伏笔和承诺被记录。
- truth 来源绑定章节号和正文 hash。

### 异常处理

- truth 提取超时：使用独立 truth timeout，失败后进入 `NEEDS_REVIEW`。
- truth 冲突：要求人工确认是设定反转还是错误。
- truth 保存失败：禁止导出。

---

## 阶段 9：格式导出

### 任务清单

- 校验章节已批准。
- 校验 truth 已提交或明确豁免。
- 按平台格式导出。
- 保存 `ExportRecord`。
- 推进状态到 `EXPORTED`。

### 输入

- 批准正文；
- `ApprovalRecord`；
- `TruthDelta`；
- 平台格式。

### 输出

- 导出文件；
- `ExportRecord`。

### 判断标准

- 文件存在且可读。
- 格式符合目标平台。
- 导出正文 hash 与批准正文 hash 一致。

### 异常处理

- 格式化失败：保留批准状态，不推进导出。
- 路径异常：拒绝写入并记录安全错误。
- truth 未提交：阻断导出，除非用户显式选择草稿导出。

---

## 阶段 10：运行复盘与下一章准备

### 任务清单

- 汇总耗时、token、错误、重试、人工干预。
- 输出 dogfood 记录或 run summary。
- 将 P0/P1/P2 问题归档。
- 为下一章准备 context package。

### 输入

- `PipelineRunRecord`；
- LLM call records；
- 审计结果；
- truth 结果；
- 用户评分。

### 输出

- `RunSummary`；
- 问题清单；
- 下一章建议。

### 判断标准

- 作者是否愿意继续写下一章。
- 本章是否需要人工二次编辑。
- 是否暴露 prompt、truth、UI 或性能问题。

---

## 8. 关键决策节点

| 决策节点 | 判断问题 | 通过条件 | 不通过处理 |
|---|---|---|---|
| 建书确认 | 题材和目标是否明确？ | 作者确认或信息完整。 | 补充 brief。 |
| 世界观确认 | 规则是否自洽？ | 无明显矛盾。 | 重生成/人工编辑。 |
| 角色确认 | 角色是否可用？ | 目标、动机、关系明确。 | 重写角色。 |
| 章节规划确认 | 章节目标是否可执行？ | plan 具体且可写。 | 重规划。 |
| 起草完成 | 草稿是否可审计？ | 字数和格式基本达标。 | 补全/重写。 |
| 审计门禁 | 是否存在 blocking？ | blocking=0。 | 修订。 |
| 修订门禁 | 修订是否改善？ | 问题减少且无新阻断。 | 回滚/人工处理。 |
| 批准门禁 | 作者是否接受？ | 人工批准。 | 编辑/修订。 |
| Truth 门禁 | 事实是否入库？ | 保存成功且无未处理冲突。 | 人工 review。 |
| 导出门禁 | 是否可发布？ | 批准正文 + truth + 格式 OK。 | 修复导出。 |

---

## 9. 异常处理与应急预案

### 9.1 LLM 超时

- 记录任务名、模型、耗时、prompt version。
- draft 支持 chunk 边界恢复。
- truth 使用独立长 timeout。
- 超过重试次数进入 `NEEDS_REVIEW`。

### 9.2 Provider 失败或限流

- 标记 provider error，不伪造输出。
- 允许用户切换 provider 后从当前阶段恢复。
- 不覆盖已有产物。

### 9.3 审计阻断

- 不允许批准。
- 自动推荐修订模式。
- 多轮失败进入人工 review。

### 9.4 修订失败

- 保留 before snapshot。
- 生成失败原因。
- 允许回滚。
- 不推进状态。

### 9.5 Truth 提取失败

- 章节保持 `APPROVED`，但标记 truth pending。
- 禁止正式导出。
- 提供重试和人工 truth 编辑入口。

### 9.6 导出失败

- 不影响批准正文。
- 不修改 truth。
- 记录失败格式、路径和错误。

### 9.7 存储失败

- 使用临时文件 + 原子替换。
- 写失败不得推进状态。
- 状态更新和产物写入应尽量同事务化或按“产物先写、状态后推”顺序。

### 9.8 页面刷新或后端重启

- 前端所有展示依赖后端持久化恢复。
- React Query 非阻塞加载。
- 未保存草稿可用 localStorage 临时兜底，但不能作为权威数据源。

## 10. Action Module 标准设计

每个流程动作都应有统一定义：

```text
action_id
name
risk_level
is_readonly
requires_confirmation
input_schema
output_schema
preconditions
side_effects
idempotency
progress_events
rollback_strategy
error_codes
next_actions
```

### 10.1 核心动作清单

| 动作 | 风险 | 是否长任务 | 是否需要确认 |
|---|---|---|---|
| create_book | 中 | 否 | 否 |
| build_world | 中 | 是 | 可选 |
| create_characters | 中 | 是 | 可选 |
| plan_volume | 中 | 是 | 可选 |
| plan_chapter | 中 | 是 | 否 |
| draft_chapter | 高 | 是 | 可选 |
| audit_chapter | 低 | 否/短 | 否 |
| revise_chapter | 高 | 是 | 是 |
| approve_chapter | 高 | 否 | 是 |
| extract_truth | 高 | 是 | 否 |
| export_chapter | 中 | 否/短 | 否 |
| run_full_pipeline | 高 | 是 | 是 |
| delete_book | 极高 | 否 | 是 |
| restore_snapshot | 极高 | 否 | 是 |

### 10.2 API / MCP / 前端统一原则

- 前端按钮调用 Action。
- MCP tool 调用同一 Action。
- AutoDirector 调用同一 Action。
- API route 只做适配，不复制业务逻辑。
- Action 返回统一 `ActionResult`。

## 11. 前端交互设计要求

### 11.1 页面结构

每章页面应展示：

- 当前章节状态；
- 当前 run 状态；
- 规划面板；
- 正文编辑器；
- 审计面板；
- 修订 diff；
- truth 摘要；
- 导出记录；
- 下一步建议。

### 11.2 长任务体验

- 显示阶段进度。
- 显示当前模型和任务名。
- 显示耗时。
- SSE 断开时提示“任务可能仍在后台运行”。
- 支持刷新后恢复 run 状态。

### 11.3 保存策略

- 权威数据全部后端保存。
- 用户输入采用 debounce PATCH。
- 保存失败必须提示。
- 不依赖 beforeunload 作为主保存机制。

## 12. 测试与验收标准

### 12.1 后端单元测试

必须覆盖：

- 每个动作输入输出；
- 状态合法推进；
- 非法状态阻断；

- 总耗时；
- 各阶段耗时；
- token；
- 失败原因；
- 审计误判；
- truth 漏提；

## 14. 最终建议

StoryForge3 的下一阶段应从“功能完成”转向“流程可信”。

推荐的最终流程基线是：

```text
所有阶段产物可追踪；
所有状态推进有门禁；
所有长任务可观察；
所有失败可恢复；
所有批准可审计；
所有导出可追溯；
前端、MCP、Agent 使用同一套动作语义。
```

只有完成该流程重设计，Phase 10B 自动导演才不会变成“把现有问题自动放大”的黑盒，而会成为一个可暂停、可检查、可恢复、可审计的小说生产系统。
